# Built-in Windows WinUSB setup

Glideleaf selects a dedicated USB Bluetooth adapter, saves that exact device, and asks Windows for administrator approval. Its own elevated helper selects the `WINUSB` model from the installed, Microsoft-signed `%SystemRoot%\INF\winusb.inf`, registers Glideleaf's device interface GUID, and installs it on the selected device instance using SetupAPI and `DiInstallDevice`. No Zadig, wdi-simple, custom driver catalog, download, or third-party installer is required for this route.

The helper and caller recheck the exact instance. Only declared USB IDs are allowed; duplicate present VID/PIDs and composite interfaces are rejected. A read-only driver probe runs before UAC. The helper checks the Microsoft INF signature again after elevation. A successful API return still requires the selected dongle to report WinUSB; reboot requests and errors are shown separately. On failure, the app reports the Windows error. It does not disable signing, security policy, or endpoint protection.

**Restore normal Bluetooth** asks Windows to install its best matching driver on the same device instance. It never deletes `winusb.inf` or another device's driver package. Restoration also requires the Bluetooth binding to be observed afterward. This path still needs a physical CSR installation and restore test. A company policy or even a personal PC's app protection can reject the application or the device change; the native API does not bypass such decisions.

`python -m glideleaf --driver-check [report.json]` is read-only and reports whether the Microsoft WinUSB model can be selected on the current Windows installation. `hardware_verified: false` means it does not prove the CSR device can be switched or used with an iPad. The app's diagnostic command is `python -m glideleaf --diagnose [report.json]`.

For signed public binary releases, `packaging/build.ps1 -Release -CertificateThumbprint <thumbprint> -Publisher <publisher> -SignToolPath <signtool.exe>` signs the application with an existing code-signing certificate. App signing and device driver signing are separate matters. The built-in WinUSB path has no Glideleaf catalog to sign. Optional hardware-specific INF/CAT tooling remains in `scripts/prepare_native_drivers.py` for future use, but it is not part of the default setup path. The v0.2.0-alpha.1 portable prerelease is explicitly unsigned and unqualified; it must not be presented as a trusted or broadly compatible release.

The current helper result channel is qualified only for same-user UAC. If a standard user enters a different administrator account, its temporary result path may be inaccessible. That case, actual CSR switching, restore, reconnect, reboot, BLE pairing, and sustained pointer/keyboard operation still need testing on the target machine.

Microsoft references: [WinUSB installation](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-installation), [driver selection list](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdibuilddriverinfolist), [exact-device installation](https://learn.microsoft.com/en-us/windows/win32/api/newdev/nf-newdev-diinstalldevice).
